## 1. Evaluation & Metric Buzzwords

### Strict Execution Accuracy (Strict EX)
- **Definition**: An evaluation metric where candidate SQL generated by an LLM is executed against a live database instance, and its returned tabular result set is compared directly against the result set of human-authored ground-truth ("gold") SQL.
- **Strict Matching Rules**:
  1. Row counts and column counts must match identically.
  2. Column names, data types, and ordering must match identically.
  3. Cell-level values must match down to numeric precision and string casing.
  4. Both result sets are sorted and serialized into a cryptographic SHA-256 hash. If hashes differ, score = 0.
- **In Our Project**: Our fine-tuned v2 model achieved **70.86% Strict EX** on the 453-query test set.
- **Why It Matters**: Prevents false positives caused by models guessing the wrong projected columns.

### Projection-Tolerant / Relaxed Execution Accuracy
- **Definition**: An execution metric that rewards candidate SQL if it retrieves the correct underlying records or answer, even if the projected column set differs from the reference SQL.
- **Example**: If the user asks *"Who are our top customers in California?"*:
  - Gold SQL: `SELECT customer_id, company_name FROM customers WHERE state = 'CA' ORDER BY spend DESC;`
  - Generated SQL: `SELECT * FROM customers WHERE state = 'CA' ORDER BY spend DESC;`
  - Strict EX flags this as a failure (different columns).
  - Projection-Tolerant EX marks this as a success because the row population and ordering are semantically correct.
- **Why It Matters**: 35.1% of natural language enterprise prompts are projection-ambiguous (the user does not state which fields to display). Tracking both strict and tolerant metrics prevents penalizing reasonable interpretations.

### Exact Match (EM)
- **Definition**: A string-matching or token-matching metric that compares the generated SQL string directly against the gold SQL string (often with whitespace normalization).
- **Flaw**: Highly brittle and penalized valid SQL variants. For example:
  - `SELECT COUNT(*) FROM orders;` vs `SELECT COUNT(order_id) FROM orders;`
  - `SELECT c.name, o.id FROM customers c JOIN orders o ON ...` vs `SELECT o.id, c.name FROM orders o INNER JOIN customers c ON ...`
- **Why We Avoid It**: A model can produce 100% semantically correct SQL that executes perfectly and yet score 0% on Exact Match.

### Syntactic Validity Rate
- **Definition**: The percentage of generated SQL queries that can be parsed by a SQL parser (e.g., `sqlglot`) and executed by the database engine without throwing a runtime error (e.g., syntax error, unknown table, missing column), regardless of whether the returned data is correct.
- **In Our Project**: Our fine-tuned model achieved **99.78% syntactic validity** (virtually zero syntax errors), whereas zero-shot base models frequently emit broken markdown fences or non-existent SQL keywords.

### Semantic Equivalence
- **Definition**: The condition where two structurally distinct SQL queries produce identical relational algebra execution trees and identical output tables across all valid database states.

## 2. Self-Correction & Agentic Loops

### Self-Correction / Repair Loop
- **Definition**: An automated agentic loop that captures execution or validation errors from an initial LLM generation attempt and feeds the error traceback back into the model in a subsequent turn, prompting it to self-diagnose and emit a corrected query.
- **Pipeline Flow**:
  1. Generate SQL candidate $Q_1$.
  2. Run static AST validation $\rightarrow$ fails with `InvalidColumnError("discount_pct")`.
  3. Formulate repair prompt: *"Your previous query generated this error: column 'discount_pct' does not exist in table 'order_items'. Valid columns are [unit_price, quantity, discount]. Please fix the SQL."*
  4. Generate repaired candidate $Q_2$.
  5. Re-validate and re-execute.
- **In Our Project**: The repair loop pushed strict accuracy from **68.43% to 70.86%** (+2.43 pp).

### Repair Execution Success Rate vs Repair Correctness Rate
- **Definition**: Two critical metrics distinguishing superficial syntactic repair from genuine semantic correction:
  - **Repair Execution Success Rate**: The percentage of broken queries that were modified to execute without throwing a database exception.
  - **Repair Correctness Rate**: The percentage of broken queries that were modified to return the exact ground-truth gold rows.
- **Empirical v2 Findings**:
  - Out of 25 failed queries entering the repair loop:
  - **17 executed successfully (68.0% Execution Success Rate)**.
  - **11 returned the correct gold data (44.0% True Correctness Rate)**.
- **Crucial Interview Insight**: Proves that 6 queries were repaired into valid syntax that executed cleanly but returned incorrect or empty rows (the "confident wrong answer" phenomenon).

### Stubborn Hallucination / Identical Query Repeat
- **Definition**: A behavioral failure mode where the LLM, despite receiving an explicit error traceback, regenerates the exact same invalid SQL query (occurring in 5 of our 25 repair attempts). Usually caused by high model prior on a specific column name or insufficient feedback context.

## 3. Fine-Tuning & Quantization

### QLoRA (Quantized Low-Rank Adaptation)
- **Definition**: An efficient fine-tuning technique that freezes a base language model quantized to 4-bit NormalFloat (NF4) and attaches small, trainable low-rank decomposition matrices (adapters) to target transformer layers.
- **Impact**: Enables fine-tuning an 8B parameter model on a single 16 GB GPU (such as Kaggle's free T4) with zero degradation in empirical benchmark quality compared to 16-bit full parameter fine-tuning.

### NormalFloat 4-bit (NF4)
- **Definition**: An information-theoretically optimal quantile quantization data type built for neural network weights that follow a normal distribution $\mathcal{N}(0, \sigma^2)$.
- **Why Better than INT4**: Standard linear 4-bit integer quantization divides the range evenly, wasting bins on low-probability outlier values. NF4 allocates equal probability mass to each bin, maximizing entropy and preserving weight information.

### Double Quantization (DQ)
- **Definition**: The process of quantizing the quantization scaling constants themselves.
- **Memory Savings**: In 4-bit quantization, scaling constants are stored as 32-bit floats every 64 weights, adding 0.5 bits per parameter. Double quantization compresses these 32-bit constants into 8-bit integers with 256-block sizes, reducing footprint from 0.5 bits/param to 0.127 bits/param (saving ~0.37 bits/param).

### Paged Optimizers
- **Definition**: Leveraging CUDA Unified Memory to automatically page optimizer state tensors between GPU VRAM and CPU RAM during gradient updates. Prevents Out-Of-Memory (OOM) crashes during long sequence training spikes.

### Completion-Only Loss (`DataCollatorForCompletionOnlyLM`)
- **Definition**: Masking the system prompt and user question tokens with the target index `-100` so PyTorch cross-entropy loss is computed exclusively on the target response tokens (the SQL output).
- **Mathematical Justification**: In our chat sequences, the system prompt and schema context exceed 1,400 tokens, while the target SQL query is only 50-100 tokens. Without completion-only loss, over 90% of gradient updates would optimize the model to predict static schema strings, diluting the domain adaptation signal.

### LoRA Hyperparameters: Rank ($r$) and Alpha ($\alpha$)
- **Rank ($r$)**: The inner dimensionality of low-rank adapter matrices $A \in \mathbb{R}^{d \times r}$ and $B \in \mathbb{R}^{r \times k}$. In our project, $r=16$.
- **Alpha ($\alpha$)**: A constant scaling factor applied to adapter updates: $W_{new} = W_{base} + \frac{\alpha}{r}(BA)$. In our project, $\alpha=32$, yielding an update scaling ratio of $\frac{32}{16} = 2.0$.
- **LoRA Dropout**: Regularization dropout applied to adapter inputs to prevent overfitting (set to 0.05).

### Target Modules
- **Definition**: The specific weight projections within the transformer architecture where LoRA matrices are injected.
- **In Our Training**: We targeted all linear projections:
  - Attention layers: `q_proj`, `k_proj`, `v_proj`, `o_proj`
  - MLP / Feed-Forward layers: `gate_proj`, `up_proj`, `down_proj`

### Thinking Mode Suppression (`/no_think`)
- **Definition**: Explicit suppression of internal reasoning / chain-of-thought tokens in models like Qwen3.
- **Why Crucial**: Without suppression, the model emits hundreds of tokens of stream-of-consciousness natural language before outputting SQL. This causes downstream parsers to crash, triples inference latency, and burns API tokens unnecessarily.

## 4. Prompt Engineering & Schema Grounding

### Schema Linking
- **Definition**: The linguistic and structural alignment between natural language entities in a user prompt and corresponding relational database entities (tables, columns, foreign-key relationships).
- **Example**: Linking the phrase *"high-priority pending orders"* to `orders.priority = 'HIGH' AND orders.status = 'PENDING'`.

### Schema Serialization
- **Definition**: The technique of formatting database schema definitions into a compact, token-efficient text string for injection into the model's system prompt (including table names, column data types, primary keys, and foreign-key join constraints).
- **Our Format**: 5,455 characters (~1,400 tokens) covering all 12 tables in a structured syntax.

### Business Glossary Grounding
- **Definition**: Explicitly embedding organizational metric definitions into the system prompt to eliminate semantic ambiguity.
- **Example**: Stating *"Revenue always denotes `SUM(order_items.unit_price * quantity * (1 - discount))`"*. This prevented the base model from guessing alternative formulations (like `SUM(total_amount)` or omitting discounts).

### Temporal Anchor (`DATA_AS_OF`)
- **Definition**: Pinning a constant reference timestamp (e.g., `DATA_AS_OF = '2024-01-01'`) into the prompt context.
- **Why Essential**: Questions like *"How many orders were placed in the last 30 days?"* are impossible to evaluate deterministically against historical test databases using dynamic functions like `CURRENT_DATE` or `NOW()`. The anchor instructs the model to calculate intervals relative to the benchmark timestamp.

### Prompt Fingerprinting
- **Definition**: Computing a cryptographic SHA-256 digest over the finalized prompt template string.
- **Why It Matters**: Guarantees that the schema context, business glossary, and instructions used during offline training, offline benchmark evaluation, and live production serving are 100% identical. Any drift immediately alerts developers via automated tests.

### Group-Level Data Splitting
- **Definition**: Partitioning training, validation, and test datasets by template family / group rather than random record sampling.
- **Contamination Prevention**: If template A (*"List top {N} customers from {Country}"*) has 50 variants, all 50 variants are placed strictly into Train OR Test. Random splitting would place variants of the same question template in both splits, inflating test accuracy through template memorization rather than generalization.

## 5. Database, Safety & MLOps Infrastructure

### Abstract Syntax Tree (AST) Parsing
- **Definition**: Parsing raw candidate SQL strings into hierarchical syntactic tree structures using `sqlglot`.
- **Application**: Allows programmatically inspecting SQL operations without executing them, identifying referenced tables and columns, validating syntax, and preventing SQL injection.

### Defense-in-Depth SQL Guardrails
- **Definition**: Layered security policies ensuring generative AI outputs can never compromise database integrity:
  1. **Layer 1: AST Statement Whitelisting**: Only AST expressions resolving to pure `SELECT` queries are permitted. Statements like `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `GRANT`, `TRUNCATE` are terminated immediately.
  2. **Layer 2: Schema Identifier Whitelist**: AST table and column identifiers are checked against the known 12-table metadata registry. References to administrative schemas (`pg_catalog`, `information_schema`) or unknown tables are blocked.
  3. **Layer 3: Engine-Level Transaction Restriction**:
     ```sql
     SET default_transaction_read_only = on;
     SET statement_timeout = '30s';
     ```
     Enforced at the connection session level on PostgreSQL so even if an adversarial bypass traversed application layers, the PostgreSQL storage engine refuses write locks and aborts runaway queries after 30 seconds.

### Observability & Distributed Tracing
- **Definition**: Instrumenting each step of the inference pipeline with end-to-end telemetry.
- **LangSmith RunTrees**: Captures hierarchical traces with child spans:
  - `Root: voice_text_to_sql`
    - `Span 1: voice_transcription` (latency, audio format)
    - `Span 2: prompt_construction` (schema version, template hash)
    - `Span 3: llm_generation` (token count, TTFT, model id)
    - `Span 4: ast_validation` (parse duration, validity boolean)
    - `Span 5: postgres_execution` (runtime latency, row count, execution status)
    - `Span 6: repair_loop` (optional feedback iteration)

### Dual-Path Speech-to-Text (STT) & Phonetic Normalization
- **Definition**: High-resilience speech processing using Gemini 2.5 Flash Audio as the primary low-latency transcription engine, with seamless fallback to Whisper-large-v3.
- **Phonetic Normalization**: A regex/phonetic mapping layer that repairs common speech recognizer corruptions of enterprise database names (e.g., converting spoken *"order underscore items"* or *"order items table"* into `order_items`).

### Cold Start & Latency Budget
- **Cold Start**: The initial latency spike (~15-45 seconds) when a serverless or containerized deployment (e.g. Render free tier or Hugging Face serverless container) spins up from zero replicas.
- **Latency Budget**: The maximum acceptable time budget for an interactive database query:
  - Speech Transcription: < 600 ms
  - LLM SQL Generation: < 1,200 ms
  - Database Execution: < 200 ms
  - **Target End-to-End Latency**: ~2.0 seconds.
